# Migration: Python/GDAL service to a Rust service

The server (`server/`) is a Flask app that shells out to GDAL and, until this
migration, to a Go program (`go-nexrad-geojson`). The client (`client/`) is a
Python service for a Raspberry Pi e-ink display. The goal is a Rust
implementation of the whole pipeline with no Go, GDAL, PROJ, or Python runtime
dependency for the server and client.

Migration is cutover per unit, not a rewrite behind a flag: each unit replaces a
working component end to end, keeps the wire protocol and output artifacts
stable, and lands with its own tests.

## Status

| # | Unit | Scope | Status |
|---|------|-------|--------|
| 1 | NEXRAD converter | Archive II -> per-elevation GeoJSON | Done: `server/nexrad-geojson` (PR #1) |
| 2a | Frame rasterization and compositing | GeoJSON gates -> byte grid, max composite, color table, RGBA PNG, street overlay; replaces the GDAL/PIL steps in `server/components/radar/render.py` | Done: `server/frame-render` (PR #2) |
| 2b | Street overlay rasterization | OSM XML -> 8-bit grayscale mask; replaces the GDAL calls in `server/setup/streets.py` | Done: `frame-render streets` (PR #3) |
| 2c | Manual inspection of a historical event | Volume + bbox -> radar/frame image by hand; add a `render-volume` command so no hand-chained steps or S3 "latest" logic is needed | Done: `main.py render-volume` (PR #4) |
| 2d | Archive -> frame in one pass | Stream Archive II gates straight into the frame renderer, dropping the per-elevation GeoJSON intermediate | Done: `frame-render frame` (PR #5) |
| 3 | HTTP/state/forecast layer | Flask app, `requests`, S3/HTTP sources, `views/`, `modes/`, `state/` | Not started |
| 4 | Pi client | HTTP polling + SPI/GPIO e-ink driver (`waveshare_epd`) | Not started |
| 5 | CI | `cargo test`, golden fixture, Python syntax checks | Not started |

## Invariants

- `/`, `/settings`, and `/frame` keep their current request and response
  semantics; the client is not migrated twice.
- `data/nexrad-latest-REF-{1,2,3}.json` keeps the current GeoJSON layout:
  `FeatureCollection`, one `Polygon` per gate, ring order A, B, D, C, A,
  `properties.value`.
- The rendered frame keeps its pixel dimensions, color table
  (`server/gdal-colors.txt`), and street overlay order.
- Every unit lands with a reproducible fixture and a golden-output comparison
  against the implementation it replaces, before that implementation is
  deleted.

## Unit 1: NEXRAD converter (done)

Replaced `bin/go-nexrad-geojson` with the local crate `server/nexrad-geojson`:

- Archive II parsing: gzip outer stream, bzip2 LDM records (concatenated
  streams), Message 31 with build-19+ data block pointers, 8/16-bit moments.
- Ellipsoidal orthographic projection implemented in Rust (ported from PROJ);
  no `proj`, `gdal`, or Go in the build.
- CLI is argument-compatible with the old binary; `server/constants/paths.py`
  now points at `bin/nexrad-geojson`.
- Golden fixture `tests/fixtures/ktlx-mini.ar2` (trimmed real KTLX volume) plus
  `ktlx-mini-REF-1.expected.json` generated by the upstream Go tool at
  `53e2aa5f`.

Acceptance evidence:

- `cargo test --all-targets` passes, including the golden comparison.
- Full KTLX volume, `--minimum 10 -e 1-3 -p REF`: output is byte-identical to
  the Go tool for all three elevations (7930 / 6647 / 3715 features).

Build and install:

```sh
cargo build --release --manifest-path server/nexrad-geojson/Cargo.toml
mkdir -p server/bin
cp server/nexrad-geojson/target/release/nexrad-geojson server/bin/
```

## Unit 2a: Frame rasterization and compositing (done)

Replaced the GDAL and PIL steps of `server/components/radar/render.py` with the
local crate `server/frame-render`, one process per frame and no intermediate
GeoTIFFs:

- GeoJSON gates -> `radar.WIDTH` x `radar.HEIGHT` byte grid over the configured
  bbox, replacing three `gdal_rasterize` runs. The input GeoJSON and the output
  grid share the WGS84 lon/lat frame, so only the affine geotransform is
  applied; the polygon scanline fill is a port of `GDALdllImageFilledPolygon`.
- Max composite of elevations 1-3, replacing `gdal_calc.py` (including its Byte
  nodata default of 255, which is what the uncovered background pixels are).
- `server/gdal-colors.txt` with nearest-color-entry lookup and alpha, replacing
  `gdaldem color-relief`.
- RGBA PNG output, replacing `gdal_translate`.
- Street mask overlay, replacing the two Pillow `paste` calls (bit-identical
  including Pillow's `+127` integer blend and `tRNS` handling).

Acceptance evidence:

- `cargo test --all-targets` passes, including the golden comparison against the
  pre-change GDAL/PIL renderer: 0 differing pixels of 355200 for the fixture in
  `server/frame-render/tests/fixtures/ktlx-mini/` (generated with GDAL 3.10.3
  and Pillow 11.1.0; see the README there).
- The same frame rendered through the new `render.py` matches the same golden
  with 0 differing pixels.
- Rasterization was additionally compared against `gdal_rasterize` for 4000
  random polygons and 300 polygons with interior rings and fractional values
  (10.4 / 10.5 / 41.4 / 254.5 / 300): 0 differing pixels.

Build and install:

```sh
cargo build --release --manifest-path server/frame-render/Cargo.toml
mkdir -p server/bin
cp server/frame-render/target/release/frame-render server/bin/
```

GDAL and PROJ are no longer required for normal frame rendering (see unit 2b).

## Unit 2b: Street overlay rasterization (done)

Replaced the GDAL calls in `server/setup/streets.py` with the
`frame-render streets` subcommand, one process per mask and no intermediate
GeoTIFF:

- Parse the Overpass OSM XML (`data/streets.osm`) into highway polylines,
  filtering ways whose `highway` tag contains `motorway` or `primary`, matching
  the Overpass query in `server/sources/osm.py`.
- Port `GDALdllImageLine` (GDAL 3.10.3 `alg/llrasterize.cpp`) for the 0/255
  polyline mask over the same bbox and frame size.
- Write `data/streets.png` as an 8-bit grayscale PNG, including the `tRNS`
  chunk for the nodata level that unit 2a's renderer already honours.
- `server/setup/streets.py` now calls `frame-render streets` instead of
  `gdal_rasterize` and `gdal_translate`.

Acceptance evidence:

- `cargo test --all-targets` passes, including the golden comparison against
  the pre-change GDAL mask: 0 differing pixels of 355200 for the fixture in
  `server/frame-render/tests/fixtures/ktlx-mini/` (generated with GDAL 3.10.3;
  see the README there).
- The mask produced through the new `setup/streets.py` matches the same golden
  with 0 differing pixels.

Build and install:

```sh
cargo build --release --manifest-path server/frame-render/Cargo.toml
mkdir -p server/bin
cp server/frame-render/target/release/frame-render server/bin/
```

GDAL and PROJ are no longer required for the radar frame pipeline. They may
still be present on developer workstations for regenerating goldens, but the
server deployment no longer depends on them.

## Unit 2c: Manual inspection of a historical event (done)

Goal: be able to point the pipeline at any past volume and inspect the resulting
radar/frame image by hand, without the server, the NWS forecast stack, or
credentials.

### Command

```sh
python3 main.py render-volume --file <path.ar2> [--minimum 10] [--force-streets]
```

`render-volume` runs the same three steps as a server frame render, but from a
local file: `bin/nexrad-geojson --minimum <n> -e 1-3 -p REF`,
`bin/frame-render radar` over the configured `[bbox]`, then
`views.storm.render([])` for the info bar and 7-colour quantization. Unit 2d
replaced the converter and `radar` steps with a single `frame-render frame`
call; the command's interface and outputs are unchanged. It skips
`nexrad_level2.latest_object()`, `boto3`, and the forecast providers; `main.py`
imports Flask, boto3, and the sources only inside the commands that use them.
It writes `data/nexrad-latest-REF-{1,2,3}.json`, `data/nexrad-latest.png`, and
`data/frame.png`, and prints the two image paths. `--file` may be
gzip-compressed.

### Street mask and `[bbox]` changes

`setup/streets.py` writes `data/streets.bbox` and `data/streets.osm.bbox` with
the bounds each artifact was built for, so `create()` no longer returns early
whenever the PNG exists:

- mask current for `[bbox]` -> no-op;
- mask generated for another bbox -> re-rasterize, and re-download
  `data/streets.osm` when that file is missing or was fetched for another bbox;
- masks and OSM files from before the stamps existed are adopted with a warning
  (no network on upgrade). Run `main.py setup --force-streets` once to have the
  geography downloaded and verified again.

`--force-streets` (on `setup` and `render-volume`) re-downloads and
re-rasterizes even when the stamps match. `render-volume` calls `create()`
first, so a missing or stale mask is rebuilt before rendering.

Evidence, in an isolated cwd with the unit 2b fixture bounds: a hand-written
`data/streets.osm` with no mask is used and stamped; a second run is a no-op;
changing `[bbox]` re-downloads the OSM and regenerates the mask; and
`--force-streets` re-downloads even when the stamps match. The mask generated
for the fixture bounds is pixel-identical to
`frame-render/tests/fixtures/ktlx-mini/streets.png` (0 differing pixels of
355,200).

### Manual steps (what the command replaces)

A reference event: the **2013 Moore EF5 tornado**, observed by KTLX (Oklahoma
City) at 20:59:14Z on 2013-05-20, a few minutes after touchdown.

Volume: `unidata-nexrad-level2`, key
`2013/05/20/KTLX/KTLX20130520_205914_V06.gz` (11.1 MB, anonymous access). It is
a build-19 V06 file with all three elevations, so no fixture copying is needed.

Bounding box: the whole supercell around the KTLX site, sized for the 800x444
frame (`0.70 deg` lon is 63.6 km at this latitude, `0.317 deg` lat is 35.3 km,
ratio 1.80 = 800/444). A bbox tight on the tornado itself only shows the core at
the frame edge; this one shows the hook and the cone of silence:

```ini
[bbox]
min_lat = 35.1615
max_lat = 35.4785
min_lon = -97.85
max_lon = -97.15
```

The same `[bbox]` drives both the radar frame and the OSM street mask, so the
streets are fetched for exactly this area.

All commands from `server/`. Requires the built binaries and the Python
requirements (Pillow, pytz, requests; boto3 and Flask only for the server
commands).

```sh
cargo build --release --manifest-path nexrad-geojson/Cargo.toml
cargo build --release --manifest-path frame-render/Cargo.toml
mkdir -p bin data
cp nexrad-geojson/target/release/nexrad-geojson bin/
cp frame-render/target/release/frame-render bin/

# 1. config: copy config/config.example.ini to config/config.ini, then set
#    nexrad_id = KTLX, forecast timezone = America/Chicago, and the bbox above.
#    (The example file ships placeholder bounds that are not a valid bbox, and
#    frame-render rejects a zero-height one.)

# 2. street mask + palette for that bbox (no-op when the mask stamp matches)
python3 main.py setup

# 3. the event volume (objects from this era are gzip-compressed)
curl -o data/nexrad-latest.ar2 \
  "https://unidata-nexrad-level2.s3.amazonaws.com/2013/05/20/KTLX/KTLX20130520_205914_V06.gz"

# 4. archive -> GeoJSON (elevations 1-3)
bin/nexrad-geojson --minimum 10 -e 1-3 -p REF -o data/nexrad-latest data/nexrad-latest.ar2

# 5. GeoJSON -> radar frame (writes data/nexrad-latest.png, 800x444)
python3 -c 'from components.radar.render import render; render()'

# 6. frame -> e-ink-ready image (info bar + 7-color quantization)
python3 -c 'from views import storm; storm.render([])'
```

Outputs: `data/nexrad-latest-REF-{1,2,3}.json`, `data/nexrad-latest.png`,
`data/frame.png` (800x480).

`-o` appends `-REF-{elevation}`, so the base name must not contain the product.
Steps 3-6 can be re-run for any volume without touching `data/streets.png`.

### What to look for

```sh
python3 - <<'PY'
import numpy as np
from PIL import Image
a = np.array(Image.open('data/nexrad-latest.png'))
print('frame', a.shape)
covered = (a[:, :, 0] != 46) | (a[:, :, 1] != 11)
print('covered pixels', int(covered.sum()), 'of', covered.size)
strong = (a[:, :, 0] > 200) & (a[:, :, 1] > 100)
print('>= 41 dBZ pixels', int(strong.sum()))
print('KTLX site is background:', bool((a[200:209, 650:659, 0] == 46).all()))
img = Image.open('data/frame.png')
print('e-ink frame', img.size, img.mode)
PY
```

Reference values for this volume and bbox: 800x444; 146,670 covered pixels of
355,200; 22,414 pixels at 41 dBZ or more; KTLX is a background-coloured 9x9
hole around `(654, 204)` (its cone of silence). `main.py render-volume --file
data/nexrad-latest.ar2` reproduces them exactly; its `data/nexrad-latest.png`
is byte-identical (SHA-256 `a823e49a...`) to the image the manual steps
produced. The mask for this bbox is empty because the Overpass fetch was
refused (see below), and `render-volume` adopted it without a refetch.

- The supercell reads as a bow of intense returns sweeping south-west to
  north-east across the upper half of the frame, with the hook wrapping toward
  the middle - the mesocyclone that produced the tornado about 15 minutes
  before this volume.
- Uncovered background is opaque `(46, 11, 119)` (unit 2a notes why), so
  "covered" above means "any gate, including the minimum value".
- `data/frame.png` is 800x480 and uses only the seven palette colours (black,
  white, red, orange, yellow, green, blue). `views.storm.render([])` passes no
  alerts, so the bottom bar shows only the timestamp.

### Known rough edges

- `render-volume` still needs `pytz` for the info-bar timestamp (via
  `components.info`); it does not need Flask or boto3.
- The Overpass API is rate limited and rejects automated clients with 4xx
  (406 from `overpass-api.de` was observed). If the download fails, write the
  query output to `data/streets.osm` yourself, delete `data/streets.png` (and
  `data/streets.bbox`) if a mask already exists, and re-run `main.py setup`.
  The hand-written file is then adopted for the current bbox and stamped:

  ```
  [out:xml];
  way["highway"~"motorway|primary"](35.1615,-97.85,35.4785,-97.15);
  out body;
  >;
  out skel qt;
  ```

## Unit 2d: Archive -> frame in one pass (done)

`frame-render frame` reads the volume, projects each gate with the same
`geojson::build_bins` geometry the converter uses, and rasterizes straight into
the per-elevation grids. The GeoJSON files are gone from the frame path:
`frame-render radar` stays for GeoJSON inputs (goldens, debugging, other
products), and `nexrad-geojson` stays as the standalone converter for the
products the frame path does not use (VEL, SW, ZDR, PHI, RHO).

### Command

```sh
frame-render frame --archive <volume.ar2> [-e 1-3] [--minimum 10]
  [--maximum <n>] --min-lon ... --min-lat ... --max-lon ... --max-lat ...
  --width 800 --height 444 --colors gdal-colors.txt \
  --streets data/streets.png --output data/nexrad-latest.png
```

`components/radar/render.py` now runs exactly this one subprocess; `render()`
keeps its signature (`volume`, `minimum`). Nothing writes
`data/nexrad-latest-REF-{1,2,3}.json` any more, and `constants/paths.py` no
longer carries the converter path or the JSON basename.

### Design

- Gate geometry, value gating (`998`/`999`, `--minimum`, `--maximum`) and
  rounding all come from `nexrad-geojson`: `build_bins` produces the rings and
  the new `geojson_coordinate` / `geojson_value` helpers round them through the
  same `{:.4}` / `{:.1}` formatting the writer uses. Both paths rasterize the
  identical numbers by construction, not by inspection.
- One byte grid per elevation preserves the within-elevation overwrite (later
  gate wins) and the cross-elevation max; the scanline fill, composite, color
  table, and street overlay are the unit 2a code, unchanged.
- The projection origin is the first radial of sweep 1, as in `nexrad-geojson`.
- `-e` uses `nexrad_geojson::elevations::parse_elevations`, shared with the
  converter, so both binaries accept exactly `N` and `N-M`. Every selected
  elevation must be present: a missing one is a hard error, matching the old
  frame path, which required all three JSON files.
- No `--emit-geojson` escape hatch: the converter is still shipped and covers
  debugging and the other products; the fused command writes only the PNG.

### Acceptance evidence

- `ktlx-mini`: fused and two-step frames are byte-identical (SHA-256
  `1dfa293b...`), and both decode to 0 differing pixels of 355,200 against the
  GDAL/PIL golden `frame-render/tests/fixtures/ktlx-mini/frame.expected.png`
  (its PNG bytes differ, as the golden came from GDAL).
  `tests/cli.rs::fused_frame_matches_the_geojson_frame` asserts the equality
  with both the two-step frame and the golden, and that the fused run leaves no
  intermediate file behind.
- 2013-05-20 20:59 KTLX volume at the unit 2c bbox with the fixture street
  mask: the fused and two-step PNGs are byte-identical (177,246 bytes, SHA-256
  `c8a90300...`).
- `components.radar.render.render()` over that volume writes
  `data/nexrad-latest.png` and no `*-REF-*.json`.

Wall clock and peak RSS for the KTLX volume above, release builds, page cache
warm, best of three (`/usr/bin/time -v`):

| Path | Wall clock | Peak RSS | Intermediates |
|---|---|---|---|
| Two-step | 0.99 s (0.84 decode+write, 0.16 rasterize) | 101 MiB | 68,051,093 bytes of JSON |
| Fused | 0.94 s | 102 MiB | none |

The volume decode dominates both paths, so wall clock only drops ~5%. The fused
path removes 68 MB of per-frame disk traffic, the second process, and the
write-then-reparse dependency on the JSON layout; peak RSS rises ~1 MiB because
the decoded volume and the frame grids coexist.

Known rough edge: `main.py render-volume` still imports `pytz` through
`views.storm`, as noted in unit 2c; that is unrelated to the frame path.

## Unit 3: HTTP/state/forecast layer

Scope: `server/main.py`, `server/server/` (Flask blueprint, `/`, `/settings`,
`/frame`), `server/views/`, `server/modes/`, `server/state/`, `server/sources/`,
`server/config/`, `server/components/`.

- Port to axum with reqwest and direct object-store HTTP (S3 listing/download),
  preserving `/`, `/settings`, and `/frame` behavior.
- Keep the schedule/state machine semantics and the forecast source selection.
- Keep `/frame` output bytes stable for a fixed radar volume and settings.

Done when the Flask process is no longer part of the deployment.

## Unit 4: Pi client

Scope: `client/main.py` and `client/radar-frame-client.service`.

- Port HTTP polling and the e-ink SPI/GPIO driver to Rust, removing the Python
  `waveshare_epd` dependency.
- Keep the existing server contract; no coordinated server change is required.
